**Two confirmed defects in the check-off path, one shared root: `retimeSchedule`

**Task 1 — the passive collapse — is bigger than the todo describes, and the
plan leads with the part the todo missed.** The todo frames it as wrong *times*:
check off a simmer promptly and its 35-minute passive window is deleted, so its
dependent collapses forward (verified: `Serve over noodles` 43 → 8). True. But
the same collapse **phantom-frees the burner the pot is physically sitting on**,
and `retimeSchedule` then places another pot there — verified: `Brown mushrooms`
moves to t=8 on a burner the bourguignon occupies until t=43. **The bug does not
produce merely wrong schedules; it produces physically impossible ones**, and it
does so with no precedence edge anywhere in the fixture. The todo's "dependents
collapse" framing understates the blast radius: *any* step competing for the same
resource can be pulled into an occupied window.

**Task 2 — the shuffle — needs its own fix and the measurements prove it.** The
list renders from `orderedByTime`, which re-sorts by live `schedule.starts` on
every tap. Fixing Task 1 removes the *common* cause (a prompt check-off fires the
collapse on literally every tap), but a **genuine overrun still shuffles after
the fix** — measured (planning_findings #5). The sort is live; you cannot fix a
live sort by making its inputs more correct, only by sorting once.

9. **THE THAW RULE IS DECIDED BY THE USER — implement it, do not re-open it, and
   do not add options.** *The display order thaws ONLY on an explicit regenerate.
   Nothing else.* The rationale, recorded here so nobody re-litigates it:
   - **Cook mode is a list a human is physically following at a stove.** Once the
     plan is being cooked, the order is a **commitment**. There is no useful
     version of "we found a better order while you're mid-session" — re-sorting
     under the cook's fingers **IS the bug**, not a feature to be preserved.
   - **Readiness chips already solve what reordering was pretending to solve.**
     `deriveReadiness` (`readiness.ts:29-38`) tells the cook what is actually
     startable; the order tells them the sequence. A step whose dependency is not
     done shows an unready chip — **the list does not need to rearrange itself to
     say so.** Reordering is a worse solution to an already-solved problem.
   - An explicit regenerate is the user **requesting a different list** — that is
     not the list moving under them. A new session loads a fresh plan and gets a
     fresh order by the same rule.

   **Therefore: NO heuristics.** No "significant overrun" threshold, no staleness
   detection, no partial re-sort, no auto-thaw. **That is where a subtler version
   of this same bug creeps back in.** If you find yourself writing any condition
   other than *"did the user hit regenerate"*, stop — it is out of scope.

   **The rule reconciles cleanly with the code — verified.** There are exactly
   THREE `setSchedule` call sites: `handleGenerateSchedule` (`:499`),
   `performRegenerate` (`:526`), `handleToggleChecked` (`:609`).
   - `handleGenerateSchedule` is **establishment, not a thaw** — its button
     renders only inside the `!schedule` branch (`:699-716`, verified), so it
     **cannot** fire while a frozen order exists. Nothing to thaw.
   - `performRegenerate` is **the one and only thaw**, and the user has already
     consented: its confirmation dialog (`:895`) says "recalculate remaining
     timing".
   - `handleToggleChecked` **never** touches the order. That is the fix.

   Both generation sites already do `setActualCompletions(new Map())` +
   `nowStartRef.current = new Map()`, so establishing the frozen order alongside
   them joins an existing, correct session-reset idiom rather than inventing a
   lifecycle. Two non-triggers, for completeness: a **refresh** re-establishes for
   free (`schedule` is React state and is **not persisted** — only `cook_progress`
   is, via `useCookProgress` — so the page returns to "Generate Prep Schedule");
   and **adding a meal** does not thaw and cannot today (the load effect keys on
   `planId` only, `:151-256`, so `mealKeyedRecipeData` never refreshes mid-session
   and `schedule` is already stale in that scenario — pre-existing, out of scope).

   **Only the ORDER freezes — times stay live.** Countdowns and start times must
   keep moving as reality does; the cards just stop being re-sorted. Make this
   distinction explicit in the code comment as well as here: `CookMode.tsx:10-14`
   already misdescribes the render path once, and must not do so again.
