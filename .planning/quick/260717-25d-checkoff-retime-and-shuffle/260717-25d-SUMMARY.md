## What shipped

### Task 1 — Floor passive at its estimate (commit `b3b9617`)

**The bug produced physically impossible schedules, not just wrong times — this is the finding the source todo missed.** Checking off a step promptly (`actualElapsed <= estActive`, the designed check-off behaviour for exactly these steps) collapsed its `passive_minutes` to 0 in `retimeSchedule`. The todo's own framing was that this mis-times a *dependent* step (`Serve over noodles` collapsing 43 → 8, reproduced). The bigger defect, verified with real prod durations (`Simmer bourguignon` 8a/35p stovetop, `Brown mushrooms` 12a/0p stovetop, `burner_count: 1`, **no precedence edge whatsoever**): the collapse phantom-frees the burner the pot is still physically sitting on, so the scheduler placed `Brown mushrooms` on that burner 35 minutes before the bourguignon pot actually comes off it — `resources.ts` meters stovetop across a step's full active+passive window precisely because a simmering pot still holds its burner, and the collapse lied to that model.

Fixed by flooring `passive_minutes` at its estimate: `passiveOcc = estPassive > 0 ? Math.max(estPassive, actualElapsed - activeOcc) : 0`, replacing the derivation that produced 0 whenever a step was checked off promptly. `activeOcc`'s `Math.min` cap is untouched byte-for-byte (out of scope — the todo's "honest model" alternative would change overrun propagation for every passive step in the app). Genuine overrun absorption still works: a simmer that really took 50 minutes still ends at 50, not pinned at 43 (verified by a new test).

**The bug and the test that could not see it shipped in the same commit.** `git log -S` confirms `5704693` ("fix checked-off step keeps active/passive split") introduced the buggy formula AND `retime.test.ts:146`, a test named after this exact bug, in the same commit — while fixing the *previous* shuffle (the third fix in this area after `3665946` and `b91ac19`). That test passes `actualElapsed = 35`, the full estimate — the full-list check-off path, where the old formula was actually correct (`actualElapsed - activeOcc` reduces to `estPassive`). It never exercised the Now-card path (`actualElapsed` active-only), which is where the collapse fires. **A path-coverage bug, not a math error** — proof of the gap: the fix passes all 326 pre-existing tests unchanged.

Three new tests added to `retime.test.ts`, all exercising the `actualElapsed <= estActive` path the suite had never touched, using the real, verified prod durations for `Simmer bourguignon`/`Brown mushrooms` (a synthetic arrangement of real durations — not a replay of the real week, where both are `just_in_time` and excluded from the week graph):
- The todo's own regression case (dependent collapse 43 → 8).
- **The phantom-burner test** — the strongest argument for the fix, with no precedence edge at all.
- Genuine-overrun absorption (a real 50-minute simmer ends at 50, not 43).

**Verified RED before committing the fix**: stashed `retime.ts` only, re-ran the two new tests, confirmed both failed against the unfixed formula (both read 8 where 43 was expected), then restored the fix and confirmed all 8 tests in the file pass.

Rewrote the `:124-137` comment block that previously encoded the opposite contract (and grew this bug once already, per `5704693`'s own reasoning) to state the check-off contract explicitly: check-off means hands-on work is finished; `actualElapsed` measures the active phase only; passive is physical and floored at its estimate, never derived from elapsed.

### Task 2 — Freeze the display order (commit `16b9c4f`)

**The shuffle survives the passive fix — measured, and that is why this task exists independently.** `orderedByTime` re-sorted a copy of `schedule.order` by live `schedule.starts` on every render, and `handleToggleChecked` calls `retimeSchedule` → `setSchedule` on every tap. A genuine overrun still crosses a neighbour's start after Task 1 removed the *common* trigger — verified with a 5a/2p bake fixture: baseline `Bake@0 Dep@7 Indep@12`, retimed with a genuine overrun to 40, `Bake@0 Indep@5 Dep@40` — Indep and Dep swap. (The brief's 5a/30p variant does NOT cross and would have made the regression test pass vacuously — used 5a/2p per the plan's own measured finding.) Corollary: crossings are reachable ONLY through passive windows — with no passive phase, a single-cook resource makes starts monotone and the sort provably cannot permute, which is exactly why Task 1 shrinks the shuffle so much without being able to close it.

Extracted the sort into a new, React-free `src/lib/scheduler/display-order.ts` — the same reason `readiness.ts` is extracted this way, and the only way this todo's own requested regression test is possible in the project's node-environment vitest with no jsdom and no `.test.tsx` support. Two pure functions:
- `freezeDisplayOrder(schedule): string[]` — the exact `orderedByTime` sort body, moved verbatim, returning ids (an ordering, not a snapshot).
- `applyDisplayOrder(schedule, frozenIds): StepInstance[]` — sorts `schedule.order` by each instance's index in `frozenIds`; `schedule.starts` is not an input. An id absent from the frozen list (cannot happen without a regenerate today) sorts to the end, tie-broken by activity-list index, and is never dropped.

Wired `displayOrder` state into `CookMode.tsx`, established at exactly the two generation call sites — `handleGenerateSchedule` and `performRegenerate` — alongside the `setActualCompletions(new Map())` / `nowStartRef.current = new Map()` reset they already perform. **The thaw rule is a fixed user decision, implemented as written, not re-opened**: the order thaws ONLY on an explicit Regenerate — no overrun threshold, no staleness detection, no partial re-sort. `handleToggleChecked` still calls `setSchedule(retimed)` on every tap and never touches `displayOrder` — that is the entire fix. Times stay live (cards keep reading `schedule.starts` directly); only the sequence freezes. Corrected the file header's claim that the order "is never permuted" to describe what actually renders now.

`display-order.test.ts` (4 tests): the residual-shuffle fixture above, asserting the crossing is real (`freezeDisplayOrder` of the retimed schedule differs from the frozen ids) *before* asserting `applyDisplayOrder` holds the frozen order — otherwise the test could pass vacuously, the exact way `retime.test.ts:146` did for the passive bug. Plus a tie-break case, an absent-id case (appended at the end, never dropped), and a filtering case (the `visibleOrder`/Now-Next contract).

**Tablet human-check NOT run this session** — the user has deferred deploying and the NAS caches the JS bundle. The invariant is pinned in CI (`display-order.test.ts`); this is the confidence check for whenever a deploy happens. Not recorded as passed.
