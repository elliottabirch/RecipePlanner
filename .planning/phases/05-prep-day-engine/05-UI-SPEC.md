# Phase 5 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

This phase delivers 5 UI surfaces (per orchestrator scope note): interactive tablet cook mode
(supersedes `BatchPrepTab.tsx`'s interactive role, keeps its print view), the GA weights panel,
step-metadata authoring fields in `RecipeEditor.tsx`'s Edit Step dialog + `StepNode.tsx` display,
the AI-backfill review page (`StepBackfill.tsx`), and 3 new linter v2 rules surfaced through the
existing Phase-1 on-demand linter panel. **No new component library or design system is
introduced** — this is an established MUI v7 + React 19 + Vite codebase (Phases 1–4 complete);
every value below is extracted from or extrapolated to match that existing system, not invented.

## Spacing Scale

Declared values (must be multiples of 4), extracted from existing MUI `sx` usage across
`ShoppingListTab.tsx`, `BatchPrepTab.tsx`, `CheckableListItem.tsx`:

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Icon-to-label gaps, chip internal padding (`gap={0.5}` = 4px in MUI's 8px spacing unit) |
| sm | 8px | Compact stacks (`gap={1}`), divider margins |
| md | 16px | Default `mb`/`p` between list items, dialog content padding (MUI default) |
| lg | 24px | Section padding, `mb={2}`/`mb={3}` between major blocks (Tabs → content) |
| xl | 32px | Layout gaps between cook-mode now/next cards and the timeline rail |
| 2xl | 48px | Also the **touch-target minimum** (see exception below) |
| 3xl | 64px | Page-level top margin (Outputs page header to tab bar) |

**Exceptions:**
- **48×48px minimum touch target** is a hard exception carried over from Phase 2's tablet pass
  (`CheckableListItem.tsx`, `ShoppingListTab.tsx` — every `Checkbox`/`IconButton` uses
  `sx={{ minWidth: 48, minHeight: 48 }}`). All new tap targets in this phase (cook-mode step-card
  tap-for-detail, check-off control, timer chip, weights-panel slider thumbs, backfill
  accept/reject buttons) MUST use this same 48px minimum — do not introduce iOS's 44px convention,
  it would be visually inconsistent with the rest of the tablet surface.
- Cook-mode now/next cards use a larger internal padding of 24px (not 16px) given the
  tablet-first, arm's-length viewing distance — this is the one phase-specific spacing exception.

## Typography

Extracted from actual `variant=` usage in `ShoppingListTab.tsx`/`BatchPrepTab.tsx` (MUI default
type scale, not overridden in `App.tsx`'s `createTheme`):

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body | 14px (MUI `body2`) | 400 (regular) | 1.43 (MUI default) |
| Label | 12px (MUI `caption`) | 400 (regular) | 1.66 (MUI default) |
| Heading | 16px (MUI `subtitle1`) | 700 (bold) | 1.5 |
| Display | 20px (MUI `h6`) | 500 (medium, MUI `h6` default) | 1.2 |

**Declared limit compliance:** 4 sizes (14/12/16/20px), 2 weights (400 regular, 700 bold — MUI's
own `fontWeight="bold"`/`"medium"` map onto these two buckets; treat `medium` (500) as belonging
to the bold bucket for this phase's new surfaces, do not introduce a third weight).

**Phase-specific usage:**
- Cook-mode now/next card step name → Heading (16px/700)
- Cook-mode scaled quantity + instructions body → Body (14px/400)
- Cook-mode countdown timer digits → Display (20px/500) — the one place a countdown needs to read
  at a glance from arm's length
- Readiness chip label ("waiting on: diced onion, cooked beans" / "Ready") → Label (12px/400)
- Weights panel slider labels → Body (14px/400); slider value readout → Heading (16px/700)
- Step-metadata authoring field labels → MUI default `TextField`/`Select` label sizing (unchanged,
  matches every other dialog in `RecipeEditor.tsx`)
- Backfill review draft-vs-current diff → Body (14px/400) for both columns; changed-field
  highlight uses weight change (400→700), never a third size

## Color

Extracted directly from `App.tsx`'s live `createTheme` call (not invented):

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `#ffffff` (MUI default `background.default`/`paper`, light mode) | Page background, card/dialog surfaces |
| Secondary (30%) | `#ff6f00` (theme `secondary.main`, orange) | Card headers, tab indicators, non-primary structural chrome — matches existing `Chip`/`Tabs` usage |
| Accent (10%) | `#2e7d32` (theme `primary.main`, green) | **Reserved for:** the cook-mode check-off control (checked state), the "Regenerate plan" primary button, the "Ready" readiness chip, the primary Save/Approve CTA in step-metadata authoring and backfill review |
| Destructive | `#d32f2f` (MUI default `error.main`) | Reject in backfill review, any future step/config delete action — not the passive/waiting readiness state (see below) |

**Accent reserved for:** the check-off toggle control, "Regenerate plan" button, "Ready" state
chip, and primary Save/Approve actions listed above — nowhere else. Do not use accent green for
decorative emphasis, borders, or non-interactive text.

**Locked project-wide rule carried forward (Phase 2 decision, `success.main` note in STATE.md):**
MUI's `success.main` is byte-identical to this theme's `primary.main` accent green. Per the
Phase-2 precedent, **never use `color="success"` for secondary/caption text** (it silently spends
the 10% accent budget) — captions and remaining-count style text always use `text.secondary`
(MUI gray), never `success.main`. This applies directly to the cook-mode "waiting on: X, Y" caption
and any "N steps remaining" summary text in this phase — use `text.secondary`, not green.

**Readiness state colors (new to this phase, must not collide with the reserved accent):**
- Waiting (not ready) → `text.secondary` (gray) caption + outlined `Chip` (no fill), matching the
  existing outlined-Chip pattern in `StepNode.tsx`'s Timing chip
- Ready → accent green filled `Chip`, label "Ready" (the one legitimate non-CTA use of accent —
  it signals the same "go" affordance as the check-off control)
- Passive/counting-down → `secondary.main` (orange) filled `Chip`, distinguishing "in progress,
  wait" from "ready to act" (green) and "blocked" (gray)

## Surface Contracts

Beyond the standard template sections above, this phase's 5 distinct surfaces each need their own
interaction contract. These are binding on the planner/executor exactly like the sections above.

### 1. Interactive tablet cook mode (`CookMode.tsx`, new page — supersedes `BatchPrepTab.tsx`'s
   interactive checklist role)

- **Layout:** now/next card pair, stacked vertically on tablet portrait, side-by-side on
  landscape ≥900px (MUI `md` breakpoint) — no new breakpoint token, reuse MUI defaults.
- **Now card:** accent-bordered (2px `primary.main`, matching `StepNode.tsx`'s existing
  `selected` border treatment: `"2px solid #1976d2"` → reuse that exact border-weight convention,
  swapped to this theme's `primary.main`), 24px padding (spacing exception, above), step name at
  Heading size, scaled quantity + instructions at Body size on tap (see tap-for-detail below).
- **Next card:** unaccented, `1px solid` gray border (matches `StepNode.tsx`'s unselected
  `"1px solid #ccc"`), same internal layout, visually recessed (no shadow, vs. now card's
  `boxShadow: 3` — reuse the exact shadow-elevation convention from `StepNode.tsx`).
- **Tap-for-detail:** tapping anywhere on a card (48px+ hit area guaranteed by card padding)
  expands scaled quantities + full instructions inline — no modal/dialog, since a dialog would
  block the check-off control underneath. Uses MUI `Collapse`.
- **Check-off control:** a single large (48×48px minimum) tap target per step, positioned at the
  card's leading edge (mirrors `CheckableListItem.tsx`'s existing `ListItemIcon` checkbox
  position/sizing exactly — reuse that component's checkbox styling, do not reinvent).
- **Live countdown (passive steps only):** Display-size (20px/500) digit readout, `secondary.main`
  (orange) color while counting, switches to accent green + "Ready" chip at zero. Countdown text
  format: `MM:SS` remaining, updates every second (no new spacing/color token needed beyond what's
  declared above).
- **Readiness state (assembly steps):** caption-size "waiting on: {productA}, {productB}" in
  `text.secondary` gray when blocked; replaced by the green "Ready" chip (see Color section) the
  instant every upstream producer is checked off in `cook_progress`. No intermediate "partially
  ready" state — AND-semantics per RESEARCH A4, so the chip is binary.
- **Check-off → retime, never reorder:** per the locked "order is authoritative, clock adapts"
  principle — checking off a step never moves any card's position in the now/next sequence, it
  only recalculates the displayed times/countdowns beneath it (already an implementation
  contract from RESEARCH.md Pattern 3; restated here as a **UI** contract too: the executor must
  not build any UI affordance — drag-to-reorder, swap-position button, etc. — that implies manual
  reordering is possible from cook mode).

### 2. GA weights panel (`WeightsPanel.tsx`, new component, likely mounted inside `CookMode.tsx`
   or as an adjacent panel/drawer on the Outputs page)

- **Layout:** one MUI `Slider` per tunable weight — `active`, `chopping` (consolidation),
  `grouping` (step-grouping), `elapsed`, `resource_pressure` — 5 sliders total, each labeled at
  Body size with its current numeric value shown at Heading size to the right of the slider (not
  inside a separate input box — avoids a 6th typography size).
  - IMPORTANT: There should be a way to boost the *active* weight above the others by default since minimizing active time is the *primary* objective (D-06) — reflect this in the initial/default weight values and slider ordering (active listed first), not by a visually distinct treatment (no extra color/size token beyond what's declared above).
- **Range:** 0–10 integer steps for each slider (matches an approachable, non-technical exposed
  range for a home cook — the underlying fitness weighting math is hidden; this is a UI-scale
  decision only, not a fitness-function change).
- **Primary CTA:** "Regenerate Plan" button, full-width on tablet, accent-colored (`contained`,
  `color="primary"`), 48px+ tall — this is the one CTA in the whole phase that should feel like a
  committed action (matches `BatchPrepTab.tsx`'s existing full-width `Button` treatment for
  "Print List", same visual weight).
- **Persistence:** slider changes write to `scheduler_config` on release (not on every drag tick)
  — debounce to avoid a sync-queue write storm; this is a UI behavior contract, not just a data
  contract.
- **No live preview:** the schedule does NOT regenerate as the user drags — only on explicit
  "Regenerate Plan" tap, per the destructive-adjacent confirmation copy above if steps are
  already checked off.

### 3. Step-metadata authoring (`RecipeEditor.tsx` Edit Step dialog + `StepNode.tsx` display)

- **Dialog additions:** append 4 new fields to the existing Edit Step `Dialog`
  (`RecipeEditor.tsx:1279+`) in this order, immediately after the existing `Step Type`/`Timing`
  fields, using the exact same `TextField`/`Select` + `margin="dense"`/`fullWidth` pattern already
  used for every other field in this dialog (`stepName`, `stepType`, `stepTiming`):
  1. `active_minutes` — `TextField` type number, label "Active minutes"
  2. `passive_minutes` — `TextField` type number, label "Passive minutes"
  3. `instructions` — `TextField` `multiline` `rows={3}`, label "Instructions"
  4. `prep_action` — `Select`, label "Prep action", options from the Phase-1 prep-verb vocabulary
     (`sliced`/`diced`/`minced`/`chopped`/`grated`/`shredded`), only shown/required when
     `step_type === "prep"` (mirrors the existing conditional-field pattern already used for the
     `Timing` select, which only shows when `stepType === "assembly"`)
  - Resource fields (`resource` select, `oven_temp_f`, `rack_slots`) follow immediately after,
    same pattern; `oven_temp_f` only rendered (and required, inline-error-validated per the Error
    state copy above) when `resource === "oven"`.
- **StepNode.tsx graph display:** surface active/passive minutes as a new small `Chip` (matches
  the existing `Timing` outlined-chip convention exactly — `size="small"`, `variant="outlined"`,
  `fontSize: "0.7rem"`, `height: 20`) reading e.g. "12m active / 30m passive" appended after the
  existing Timing chip, same `Box display="flex" gap={0.5}` row. Do not introduce a new chip
  visual style — reuse the exact `sx` block already in `StepNode.tsx:60-70`.
- **No new destructive action** in this surface — Save/Cancel copy stays exactly as-is.

### 4. AI-backfill review page (`StepBackfill.tsx`, new page)

- **Layout:** per-recipe-batch review list. Each step shows a two-column draft-vs-current diff
  (draft on left, current/blank on right for net-new fields) — Body size (14px/400) for both
  columns; any field the draft *changes* from current is bold-weighted (700) to draw the eye,
  matching the same weight-only-differentiation rule as Typography section above (no color-coding
  the diff — color is reserved for the accent/destructive roles already declared).
- **Per-field controls:** "Accept" (default-checked, accent-styled once accepted) / "Edit" (opens
  inline `TextField` matching the field's authoring-dialog counterpart from Surface 3 — e.g. the
  same multiline `instructions` `TextField`) — never a full modal, this is a review flow that
  should read top-to-bottom on one scrollable page.
- **Batch-level CTA:** "Save Reviewed Batch" — accent green, `contained`, disabled until every
  step in the current batch has an explicit Accept/Edit decision (no silent "leave as draft"
  default — matches PREP-02's "reviewed in batches" requirement literally).
- **Idempotency signal:** once a batch is saved, its steps drop out of the review queue
  (re-running backfill on an already-complete recipe should show 0 items, not stale drafts) — the
  "All caught up" empty state (Copywriting Contract) is the expected terminal state per recipe.
- **No destructive confirmation on Reject** (see Copywriting Contract) — this is the one place in
  the whole app's established pattern where a "reject/discard" action deliberately does NOT use
  the standard "Are you sure..." dialog, because the record being discarded is a disposable AI
  draft, not user-authored data. Document this explicitly so the checker doesn't flag its absence
  as a gap.

### 5. Linter v2 findings (extends existing Phase-1 on-demand linter panel)

- **No new UI surface.** Reuse `Products.tsx`'s exact `Dialog` + `Alert severity={finding.severity}`
  per-finding pattern (`Products.tsx:522-559`) verbatim for the 3 new rules
  (`missing-durations`, `missing-prep-action`, `missing-pull-step`). The "Lint" trigger button,
  dialog chrome, and `findings.length === 0` empty-state copy pattern
  ("No issues found — all X are clean.") all carry over unchanged — only the underlying
  `runLint`/rule functions are new (a `lib/` concern per RESEARCH.md, not a UI concern).
- If the linter's dialog is now shown from more than one surface (e.g. also invoked from within
  `RecipeEditor.tsx` or `CookMode.tsx` for the week-scoped `missing-pull-step` rule), the dialog's
  visual treatment must stay byte-identical across call sites — do not create a second dialog
  style for the "same feature, different launch point" case.
