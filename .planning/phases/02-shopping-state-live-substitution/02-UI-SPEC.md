# Phase 2 — UI Design Contract

> Visual and interaction contract for Phase 2: Shopping State & Live Substitution.
> Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Scope note:** This project has an established design system already — MUI 7
(Material UI) with a custom `createTheme` in `src/App.tsx` (green primary
`#2e7d32`, orange secondary `#ff6f00`), no Tailwind/shadcn anywhere in the repo.
Per the orchestrator's explicit instruction, this contract **reuses MUI
components and the existing theme** rather than introducing a new design
system. The shadcn initialization gate was evaluated and skipped: this is a
Vite+React app, but its component library is MUI, not Radix/shadcn primitives
— installing shadcn now would fork the design system mid-project. `Tool: none`
below reflects that decision, not an oversight.

## Spacing Scale

MUI's default `theme.spacing()` unit is **8px** — this is already the app's
de facto scale (existing code uses `mb={2}`, `gap={1}`, `p={1.5}` etc.
throughout `Outputs.tsx` and its tab components). This phase adopts the
standard 8-point scale as MUI spacing multiples — no new scale needed.

| Token | Value | MUI `sx` shorthand | Usage |
|-------|-------|---------------------|-------|
| xs | 4px | `0.5` | Icon-to-label gaps, chip internal padding |
| sm | 8px | `1` | Compact element spacing, gap between adjacent controls (swap/make-it icon buttons) |
| md | 16px | `2` | Default element spacing, dialog content padding, gap between list sections |
| lg | 24px | `3` | Section padding (store/section groupings, dialog section breaks) |
| xl | 32px | `4` | Layout gaps (rare this phase) |
| 2xl | 48px | `6` | Not used this phase |
| 3xl | 64px | `8` | Not used this phase |

**Exception — tablet touch targets (SHOP-06):** every net-new interactive
control this phase (have-N stepper buttons, swap icon button, make-it icon
button, quick-create dialog fields' tap zones, resolution chip's tap zone,
checkbox tap zone) must have a **minimum 48×48px tap target**, per Material
Design's touch-target guidance
`[CITED: m2.material.io/develop/web/supporting/touch-target]` — this is the
same guidance RESEARCH.md's Pitfall #6 already flags against the existing
`CheckableListItem`'s `size="small"` checkbox. The *visual* glyph (checkbox,
icon) may stay small; the *hit area* (via `sx={{ minWidth: 48, minHeight: 48 }}`
on the enclosing `IconButton`/`ListItemIcon`, or `size="medium"` on `IconButton`
which already renders ~48×48 by MUI default) must not shrink with it.
Minimum 8px (`sm`) gap between any two adjacent 48px tap targets, to avoid
mis-taps on a moving tablet at the store.

## Typography

Declaring exactly 4 sizes and 2 weights, scoped to this phase's new and
touched surfaces (have-N stepper, swap dialog, quick-create dialog, make-it
confirm dialog, sync indicator, resolved-line treatment). Existing MUI
variant defaults elsewhere in the app (`h4`, `h6`, `caption`, etc.) are
unchanged by this contract — this table governs the phase's new UI only.

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Label | 12px | 400 (regular) | 1.4 |
| Subtitle | 14px | 600 (semibold) | 1.3 |
| Body | 16px | 400 (regular) | 1.5 |
| Heading | 20px | 600 (semibold) | 1.2 |

**Role mapping:**
- **Label (12/400)** — secondary/meta text: recipe-source captions, remaining-to-buy caption ("3 to buy"), sync indicator status text, resolution chip labels.
- **Subtitle (14/600)** — section headers inside dialogs ("Meals using {product}", "Replace with"), store/section group headers (matches existing `fontWeight="bold"` pattern in `ShoppingListTab.tsx:162,218` — override MUI's default bold weight of 700 to this contract's 600 via `sx={{ fontWeight: 600 }}` for consistency).
- **Body (16/400)** — shopping-line primary text (product name + quantity), dialog body copy, form field input text, confirm-dialog prompt text. This is a deliberate step up from the existing dense list's font size, in service of SHOP-06 tablet readability — apply via explicit `primaryTypographyProps={{ variant: "body1" }}` rather than relying on MUI `List dense`'s implicit sizing.
- **Heading (20/600)** — dialog titles (`DialogTitle`) for the swap dialog, quick-create dialog, and make-it confirm dialog.

Only two font weights across all four roles: **400 regular** and **600
semibold**. Do not introduce MUI's default bold (700) or medium (500) for
any net-new element this phase.

Accent (`#2e7d32`) reserved for exactly: primary CTA buttons in the three new
dialogs (Save Swap / Create Product / Add to This Week), the existing Copy to
Clipboard button, checkbox-checked fill, and selected/active row highlight.
Do not use accent for section headers, chips, or general emphasis — that is
the Subtitle typography role's job, not color's.

The existing theme's secondary orange (`#ff6f00`) is **not** used by any new
element this phase — it stays reserved for whatever the app currently uses it
for elsewhere; introducing a second accent usage would break the 10% budget.

## Phase-Specific UI Surfaces

Prescriptive detail for the seven surfaces this phase touches, per the
orchestrator's focus list. All controls reuse existing MUI components
(`Dialog`, `List`, `Checkbox`, `IconButton`, `Autocomplete`, `Chip`) — no new
component primitives.

### 1. Have-N stepper (`ShoppingListTab.tsx`)
- Layout: inline at the right edge of each non-pantry shopping `ListItem`, replacing/augmenting the existing `CheckableListItem` row.
- Controls: `IconButton size="medium"` (Remove, `RemoveIcon`) — numeric value display (min-width 40px, centered, Body role 16/400, or Subtitle 14/600 if bold emphasis wanted for the "have" count) — `IconButton size="medium"` (Add, `AddIcon`). Each `IconButton` is a 48×48 tap target per the Spacing Scale exception; `sm` (8px) gap between the two buttons and the numeric display.
- Remaining-to-buy caption: Label role (12/400), directly under or beside the product name — "{n} to buy" while `remaining > 0`; "All set" (color `success.main` or `text.secondary`, not accent green, to avoid overloading the 10% accent budget) when `remaining ≤ 0`.
- Auto-complete visual (have ≥ needed): row opacity `0.55`, primary text `textDecoration: line-through` — same visual language as the existing `CheckableListItem` checked state (`CheckableListItem.tsx:32-36`), so a resolved-via-have-N line looks identical to a resolved-via-make/skip line (per D-05, "resolved" is one visual family regardless of cause).
- Lines with no quantity (pantry-style) keep the existing simple checkbox — no stepper added.

### 2. Dimmed/struck resolved-line treatment (D-05, applies to all resolution causes)
- Applies whenever `resolution !== 'buy'` OR `have ≥ needed`.
- Visual: `opacity: 0.55` on the entire `ListItem`; primary text `textDecoration: line-through` (Body role, 16/400) — matches existing `CheckableListItem` checked styling, extended to the whole row rather than just the checkbox.
- A small `Chip size="small"` at the row's trailing edge shows which resolution applies — "Making" / "Skipped" / "Have enough" (Label role, 12/400, neutral grey `variant="outlined"`, not accent-colored — resolution state is informational, not a call to action).
- The chip itself is the un-resolve affordance: tapping it toggles `resolution` back to `buy` (or clears `have_quantity` if that was the cause). Wrap the chip in a container with `minWidth: 48, minHeight: 48` padding so the *tap target* meets the touch minimum even though the *chip* renders small — same small-glyph/large-hit-area pattern as the checkbox (Pitfall #6).
- Resolved lines stay visible on-screen (never removed from the DOM/list) — only the export path filters them out (D-06). No animation/collapse on resolve; the row dims in place so the "easy to un-resolve at a glance" requirement (D-05) is satisfied by the item never moving.

### 3. Mid-shop swap dialog (`ShopSwapDialog.tsx`, new)
- `Dialog maxWidth="sm" fullWidth` (single-column flow — this is simpler than `VariantEditorDialog`'s two-panel node-list-plus-editor layout, since it operates on one product across checked meals, not a whole recipe's node graph).
- `DialogTitle` (Heading role, 20/600): `Swap {productName}`.
- `DialogContent dividers`, top to bottom:
  1. **Meals section** — Subtitle label "Meals using {productName}". `List dense` of checkable rows, one per `SwapTarget` (meal), each row: `Checkbox size="medium"` (48px tap target) + `ListItemText` (Body role, meal/recipe name) + an inline quantity `TextField` (type number, width ~72px) and unit `Select` (width ~96px, bound to `units.ts`'s enum per D-12) — both **pre-filled with the original node's quantity/unit** (D-07) and only editable when that meal's checkbox is checked (disabled/greyed otherwise). If a meal has more than one matching node, fan out one qty/unit input per checked meal, applied to all its matching nodes (per RESEARCH.md's recommended interpretation of D-07 — confirm during planning if this needs revisiting).
  2. `Divider` (`sm`/8px vertical margin).
  3. **Replacement section** — Subtitle label "Replace with". `Autocomplete` reusing `VariantEditorDialog`'s existing pattern (`VariantEditorDialog.tsx:312-338`): type-colored `ProductIcon` per option, `groupBy` product type. Below the Autocomplete, an inline text-button/link: "+ Create new product" — opens the Quick-Create dialog (surface 4) as a **nested modal**, not a navigation. On save, the newly created product is returned directly into this Autocomplete's selected value (D-08) — the shopper never leaves the swap flow.
  4. If the meals list would be empty (edge case — see Copywriting Contract), show the empty-state heading/body instead of the checklist.
- `DialogActions`: "Cancel" (text button) + "Save Swap" (`variant="contained"`, accent color, disabled until ≥1 meal is checked **and** a replacement product is selected).
- On save: writes/extends `meal_variant_overrides` per checked meal (delete+recreate pattern, mirroring `WeeklyPlans.tsx:476-499`), including the new `quantity`/`unit` fields (D-09) — then bumps `refreshCounter` to re-derive all six outputs.

### 4. Quick-create dialog (`QuickCreateProductDialog.tsx`, new)
- Nested `Dialog maxWidth="xs" fullWidth`, opened from within the swap dialog (surface 3) — stacks on top, does not replace it.
- `DialogTitle` (Heading role, 20/600): "Create Product".
- `DialogContent`, exactly the fields the decision record specifies — no more:
  - Name — `TextField` (autofocus, required, Body role for input text).
  - Store — `Select`/`Autocomplete` over existing `stores` (optional).
  - Section — `Select`/`Autocomplete` over existing `sections` (optional).
  - Unit — `Select` bound to the Phase-1 unit enum (`src/lib/units.ts`, per D-12 — not free text), required.
- `DialogActions`: "Cancel" + "Create Product" (`variant="contained"`, accent color, disabled until Name and Unit are filled — Store/Section stay optional per the "ruthlessly minimal" phone-friendly intent).
- On success: dialog closes, returns the created `Product` into the parent swap dialog's replacement Autocomplete (auto-selected) — per D-08, this never bounces the shopper out of the swap flow.
- On failure: inline `Alert severity="error"` inside the dialog with the quick-create error copy (Copywriting Contract) — do not close the dialog on failure, preserve the user's typed input.

### 5. Make-it confirm flow
- Line action "Make it" appears **only** when `product.source_recipe` is set (D-10). Per D-10's "disabled/hidden" choice, this contract's discretion: **hide entirely** when ineligible (no `source_recipe`) rather than showing a disabled control — a dead-end disabled button on a touch device invites confused re-taps with no feedback path; omitting it entirely is cleaner for the store-shelf use case.
- Eligible state: `IconButton size="medium"` (48×48 tap target) with a "make it at home" icon (e.g. `HomeIcon` or `RestaurantIcon`), positioned alongside the Swap action.
- Tap opens a confirm-first `Dialog maxWidth="xs"` (D-11 — never mutate the plan on a single tap):
  - `DialogTitle` (Heading, 20/600): "Make it instead of buying?"
  - `DialogContent`: Body role (16/400) prompt — "Add {recipeName} to this week and make it instead of buying {productName}?"
  - `DialogActions`: "Cancel" + "Add to This Week" (`variant="contained"`, accent color).
- On confirm: calls the existing `handleAddRecipeToPlan` (`Outputs.tsx:562-576`) and sets `shopping_state.resolution = 'make'` for the line — do **not** wire this button directly to `handleAddRecipeToPlan` the way `OutOfStockSection.tsx:145` does (that path has no confirmation and is the wrong prior art here, per RESEARCH.md Pitfall #4).
- After confirm, the line immediately shows the dimmed/struck resolved treatment (surface 2) with a "Making" chip.

### 6. Pending-sync indicator (`SyncIndicator.tsx`, new)
- Location: Outputs page header, inline near the Weekly Plan `Select` (`Outputs.tsx` header box, ~line 614-654) — right-aligned, `sm` (8px) gap from the plan selector.
- A compact status element, ~32px tall, Label role (12/400) text:
  - **Synced** (pendingCount === 0, no failures): `CloudDoneIcon` (`fontSize="small"`, `color="action"`/grey — not accent green, to keep the 10% accent budget for actionable CTAs only) + "Synced".
  - **Saving** (pendingCount > 0): `CircularProgress size={14}` (or a `CloudSyncIcon`) + "Saving… ({n})" where `{n}` = `pendingCount`.
  - **Retry-exhausted / can't reach server** (a write has exhausted its retry attempts but remains queued, per D-13's in-memory-only queue): `CloudOffIcon` `color="warning"` + "Can't reach server — retrying" (MUI `warning.main`, not `error.main` — this is a transient/recoverable state per the phase's optimistic-retry design, not a hard failure).
- No dedicated empty/idle-hidden state — the indicator is always present in one of the three states above, so the shopper has a persistent, glanceable connectivity signal while at the store.
