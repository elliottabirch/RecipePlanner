# Phase 3 — UI Design Contract

> Visual and interaction contract for Phase 3: Product Registry Seeding.
> Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Scope note:** Per the orchestrator's framing, this phase is data + search
plumbing — the UI surface is deliberately **small and lives inside existing
components**. This contract covers exactly three things: (1) fuzzy-search
result presentation across four existing surfaces, (2) the new "Search USDA"
mode inside the existing Phase-2 quick-create dialog, and (3) a note on
registry-page scale. It does **not** introduce a nutrition UI, new pages, or
the deferred density/purchase-unit model — those stay out of scope per
CONTEXT.md.

This project has an established design system already — MUI 7 (Material UI)
with a custom `createTheme` in `src/App.tsx` (green primary `#2e7d32`, orange
secondary `#ff6f00`), no Tailwind/shadcn anywhere in the repo. Per Phase 2's
precedent (`02-UI-SPEC.md`), the shadcn initialization gate is evaluated and
skipped again here for the same reason: this is a Vite+React app, but its
component library is MUI, not Radix/shadcn primitives — installing shadcn now
would fork the design system mid-project (this would be the third phase to
skip it in a row). `Tool: none` below reflects that decision, not an
oversight. This contract **reuses the exact typography/color roles Phase 2
already established** so the app's search/dialog surfaces stay one visual
language, not two.

## Spacing Scale

Reuses the app's de facto 8-point scale (MUI's default `theme.spacing()` unit)
— same tokens as Phase 2, no new scale needed.

| Token | Value | MUI `sx` shorthand | Usage this phase |
|-------|-------|---------------------|-------------------|
| xs | 4px | `0.5` | Gap between a USDA result row's name and its category chip |
| sm | 8px | `1` | Gap between the mode-toggle tabs and the field/results area below them; gap between stacked USDA result rows |
| md | 16px | `2` | Dialog content padding (unchanged from existing quick-create dialog); gap between the search field and the results list |
| lg | 24px | `3` | Not used this phase |
| xl+ | 32px+ | `4`+ | Not used this phase |

**Exception — tablet touch targets:** every USDA search-result row is a full
`ListItemButton` with **minimum 48px height** (Material touch-target
guidance, same citation as Phase 2's contract), full dialog width tap target
— not a small chip or icon. The mode-toggle `Tab` controls use MUI's default
`Tab` height (48px), already compliant with no override needed.

## Typography

Declaring the same 4 roles Phase 2 established, reused verbatim for
consistency. This phase's new surfaces (USDA result rows, mode tabs,
no-results copy) map onto these existing roles — no new sizes introduced.

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Label | 12px | 400 (regular) | 1.4 |
| Subtitle | 14px | 600 (semibold) | 1.3 |
| Body | 16px | 400 (regular) | 1.5 |
| Heading | 20px | 600 (semibold) | 1.2 |

**Role mapping (this phase's surfaces):**
- **Label (12/400)** — USDA result row's category caption ("Vegetables and Vegetable Products"), no-results/empty-state helper copy, results-counter caption ("Showing N of M products," already existing on the registry page), the "fdc:{id}" prefill-confirmation chip text.
- **Subtitle (14/600)** — Mode-toggle tab labels ("Enter manually" / "Search USDA") — MUI `Tab`'s default label styling already renders at 14px; override weight to 600 via the theme's existing subtitle convention if MUI's default (500) is used, per the "only 400/600, never 500/700" rule.
- **Body (16/400)** — USDA result row's primary text (food name), all existing search-field input text (registry search, Autocomplete inputs, dup-check name field) — unchanged, this phase doesn't touch input font size.
- **Heading (20/600)** — Dialog title "Create Product" (unchanged, already this weight/size in `QuickCreateProductDialog.tsx:97`).

Only two font weights across all roles: **400 regular** and **600
semibold** — matches Phase 2's rule, do not introduce MUI's default bold
(700) or medium (500) for any net-new element this phase, including the tab
labels.

## Color

Reuses the existing theme; no new palette introduced.

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `#ffffff` | Page background, dialog background, list surfaces — unchanged |
| Secondary (30%) | `#f5f5f5` (MUI `grey.100`) | USDA result row hover/selected background, `Divider`-bounded sections — unchanged from Phase 2 |
| Accent (10%) | `#2e7d32` (theme `primary.main`) | Reserved for: the active mode-toggle tab's indicator underline and selected-tab text color (MUI `Tabs` default behavior — no override needed, it already uses `theme.palette.primary`); the existing "Create Product" primary CTA button; the prefill-confirmation chip's outline color (`variant="outlined" color="success"` is **not** used here — see note below) |
| Destructive | `#d32f2f` (MUI default `error.main`) | Reserved for: existing "Delete Product" action on the registry page (unchanged). No new destructive action this phase. |

Accent (`#2e7d32`) reserved for exactly: the selected mode-toggle tab
indicator/label, the "Create Product" CTA (unchanged from Phase 2's contract
for the same button), and the row-selected state on a tapped USDA result
(brief highlight before the tab switches). Do **not** use accent for the
prefill-confirmation chip — use a neutral `variant="outlined"` chip with
default `text.secondary` border/text, not `success.main` or accent green, to
avoid overloading the 10% accent budget (same rule Phase 2 applied to the
have-N stepper's "All set" caption). Do not use accent for the results-count
caption or the no-results empty state — those are Label-role neutral text.

## Phase-Specific UI Surfaces

Prescriptive detail for the three surfaces this phase touches. All controls
reuse existing MUI components (`Tabs`, `List`, `ListItemButton`, `TextField`,
`Chip`, `Autocomplete`) — no new component primitives, no new dialogs beyond
extending the existing `QuickCreateProductDialog`.

### 1. Fuzzy-search result presentation (four existing surfaces, REG-02)

**What changes visually:** result **ordering** (best match first) and
**empty-state copy** only. No new chrome, no highlighted/bolded matched
substrings — `searchProducts()` reorders the same option list each surface
already renders; `renderOption`/table-row markup is untouched.

- **Registry page (`Products.tsx:99-106`)** — `filteredItems` swaps its
  `.includes()` body for `searchProducts(searchQuery, items)`. The existing
  "Showing {n} of {m} products" counter and "No products match your search"
  empty state (already present, `Products.tsx:328-341`) require **no copy
  change** — fuzzy search only changes which items populate `filteredItems`.
- **RecipeEditor product Autocompletes (`:900-904`, `:1144-1148`)** — add
  `filterOptions={(options, { inputValue }) => searchProducts(inputValue, options)}`.
  Add `noOptionsText="No products match \"{inputValue}\""` (dynamic string,
  built from the Autocomplete's current input state) replacing MUI's default
  "No options" — the existing "+ Create New Product" button just above each
  Autocomplete (`:896`) is the action path out of this empty state; no new
  button needed.
- **ProductForm duplicate-check (`:229-251`)** — `potentialDuplicates` swaps
  its `includes`/`includes` body for
  `searchProducts(searchTerm, existingProducts).slice(0, 5)`. The
  error/warning `Alert` treatment (`:277-280`, existing severity + copy) is
  unchanged — fuzzy search improves *recall* (catches "garbonzo" typing
  against "garbanzo") without changing the warning's visual design.
- **ShopSwapDialog replacement-product Autocomplete (`:298-324` per
  03-RESEARCH.md)** — same `filterOptions` + `noOptionsText` wiring as
  RecipeEditor's Autocompletes, for visual consistency across every
  Autocomplete-based product picker in the app.

No match-highlighting (no bolded/underlined matched characters) is in scope
this phase — reordering + the no-results copy above is the entire visible
contract. This is a deliberate simplicity call: the behavior bar in
CONTEXT.md ("garbonzo"→"garbanzo", "paste tomato"→"tomato paste") is about
*which result ranks first*, not about visually marking why it matched.

### 2. "Search USDA" mode inside quick-create dialog (`QuickCreateProductDialog.tsx`, REG-03)

- **Toggle affordance:** a `Tabs value={mode} onChange={...} variant="fullWidth"`
  row inserted directly below `DialogTitle`, above the existing form fields.
  Two tabs: **"Enter manually"** (default/first, preserves today's exact
  behavior) and **"Search USDA"**. `sm` (8px) margin between the tab row and
  the content below it. This is the only new top-level layout element in the
  dialog — everything else nests inside whichever tab is active.

- **"Enter manually" tab (existing behavior, unchanged):** the four fields
  already in the dialog today — Name, Store, Section, Unit — exactly as
  currently implemented (`QuickCreateProductDialog.tsx:106-170`). This tab's
  content is not touched by this phase except to receive prefilled values
  when a USDA result is selected on the other tab (see below).

- **"Search USDA" tab (new):**
  - A `TextField` search box (full width, `size="medium"`, `InputAdornment`
    `SearchIcon` — same visual pattern as the registry page's existing
    search field), placeholder "Search USDA foods…", autofocus when the tab
    becomes active.
  - Below it, a `List dense={false}` of result rows — each a
    `ListItemButton` (full-width tap target, min-height 48px) showing:
    primary text = food name (Body role, 16/400), secondary text = the
    category (Label role, 12/400, `text.secondary`) — e.g. "Vegetables and
    Vegetable Products". `xs` (4px) internal gap between the two lines.
  - **Lazy load:** the bundled `usda-sr-legacy.json` asset is fetched/parsed
    only the first time this tab is activated in a session (not on dialog
    mount) — while loading, show a centered `CircularProgress` + "Loading
    USDA catalog…" (Label role) in place of the list. Subsequent tab
    activations within the same session reuse the already-parsed in-memory
    index — no repeat loading state.
  - **Empty-query state** (list focused, nothing typed yet): centered Label
    role text, "Type to search the USDA catalog" — no list rendered.
  - **No-match state** (query typed, zero results): centered Label role
    text, "No USDA matches for \"{query}\". Try a different term, or switch
    to \"Enter manually\"." — this is the explicit fallback path back to
    plain name-only creation (REG-03's "fallback to plain name-only
    creation" requirement); no button needed beyond directing the user back
    to the other tab, since the tab row is always visible above.
  - Results are **not paginated** — cap the rendered list at the top ~20
    matches from `searchProducts()` (same pattern as ProductForm's existing
    `.slice(0, 5)` cap, scaled up since this is a dedicated full-list view
    rather than an inline warning) to keep the tablet render light.

- **Selection → prefill feedback:** tapping a result row:
  1. Immediately switches the active tab back to **"Enter manually"**.
  2. Prefills **Name** (editable — the USDA name is a starting point, not
     locked) and **Section** (editable `Select`, matched via the bundled
     index's category→section map) from the selected row.
  3. Shows a small neutral `Chip size="small" variant="outlined"` reading
     "USDA match · fdc:{fdcId}" directly beneath the Name field (Label role,
     `text.secondary` border/text — not accent-colored, per the Color
     contract above) as non-blocking confirmation that the prefill
     succeeded and which USDA record backs it.
  4. **Store** is left blank (USDA carries no store concept) and **Unit**
     is left blank and required, exactly as today — per 03-RESEARCH.md Open
     Question 4's recommendation, Search-USDA does not attempt to
     auto-derive `canonical_unit` (SR Legacy carries no purchase-unit
     concept, same reasoning as the seed itself under D-04). Move focus to
     the **Unit** `Select` after prefill, since it's the one remaining
     required field the user must complete — this is the single most
     useful "what do I do next" cue on a tablet form.
  - `isValid` is unchanged: `name.trim().length > 0 && unit !== ""` — a
    USDA-sourced product still requires the user to explicitly pick a unit
    before "Create Product" enables, same validation gate as manual entry.

- **On create (either tab):** the created `Product` carries
  `usda_data_type = "sr_legacy"` and the matched `fdc_id`/`usda_category`
  when sourced from the USDA tab (data-plumbing, per D-06 — not a visual
  concern, noted here only so the planner doesn't lose the connection
  between this UI flow and the schema fields it populates).

### 3. Registry-page breadth (REG-01, no new chrome)

The registry page's existing `Table` (unchanged component,
`Products.tsx:334-465`) and its existing search field + results counter
already scale to the expected post-seed size (roughly the existing 291 plus
up to a few hundred net-new raw products, per 03-RESEARCH.md's coverage
estimate) without pagination or virtualization — this matches the
no-virtualization precedent already set across the app (no list anywhere in
the codebase is currently paginated or virtualized). **No pagination or
scroll-area change is introduced this phase.** If the registry later grows
past roughly 1,000 rows and render performance becomes a concern, that is a
future-phase consideration, not this phase's obligation — flagged here only
so the planner doesn't need to re-derive this judgment call.
